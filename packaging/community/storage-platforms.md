# Incremental backups across OpenShift storage platforms

As of **25 November 2026**, you can obtain an incremental recovery point in several ways. To compare two products, ask how many bytes they **read from the source**, how many they **send to backup storage**, and what you need to restore after losing the original storage array. A driver snapshot handle, an array replica and an independently readable S3 backup have different recovery dependencies.

## The platform and the VM

| Mechanism | Available interfaces and support level |
| --- | --- |
| VM writes through QEMU | QEMU dirty bitmaps track modified regions between checkpoints. Libvirt can push backup data to a target or expose ranges through NBD. KubeVirt wraps this in VM backup, tracker and export APIs. This can work for VM disk images on ordinary Linux NFS. Writes by a pod to the same share bypass the hypervisor. [QEMU bitmaps](https://www.qemu.org/docs/master/interop/bitmaps.html) · [Libvirt backup](https://libvirt.org/formatbackup.html) |
| OpenShift Virtualization | OpenShift and OKD 5.0 are released. Red Hat still labels storage-agnostic QEMU changed-block VM backup **Technology Preview** in OpenShift Virtualization 5. Upstream KubeVirt 1.10 promoted the main incremental API to Beta and added per-volume recovery after bitmap loss. Its separate offline incremental gate is Alpha. The distribution and its backup consumer choose which APIs and modes they support. [Red Hat Virtualization 5](https://www.redhat.com/en/blog/unlocking-next-generation-workloads-whats-new-red-hat-openshift-virtualization-5) · [KubeVirt 1.10](https://kubevirt.io/2026/changelog-v1.10.0.html) · [KubeVirt feature gates](https://pkg.go.dev/kubevirt.io/kubevirt@v1.10.0/pkg/virt-config/featuregate) |
| CSI snapshots and volume groups | A snapshot provides a point on the driver’s storage. A volume group snapshot coordinates that point across qualifying PVCs. In OpenShift the group feature went from Technology Preview in 4.18 to GA in 5.0 with supporting drivers, including documented ODF support. A group point still needs an export and a tested restore for independent protection. [Kubernetes group snapshots](https://kubernetes.io/blog/2026/05/08/kubernetes-v1-36-volume-group-snapshot-ga/) · [OCP release notes](https://docs.redhat.com/en/documentation/openshift_container_platform/5.0/html/release_notes/ocp-5-0-release-notes) |
| CSI changed-block metadata | A compatible service returns allocated ranges for one block-backed snapshot or changed ranges between two. The reader must still read and retain the data. Upstream CSI CBT is Beta. OpenShift introduced Developer Preview in 4.20 and moved to Technology Preview in 5.0. Network filesystems require a file-aware or storage-native alternative. OKD 5.1 is an engineering candidate at this review date. [CSI interface](https://kubernetes-csi.github.io/docs/changed-block-tracking.html) · [Upstream Beta status](https://kubernetes.io/blog/2026/09/14/csi-changed-block-tracking-beta/) · [OKD 5.0 notes](https://okd.io/blog/2026/09/17/okd-5.0-release-notes/) |

## What the underlying storage offers

| Storage | Where changes can be found |
| --- | --- |
| Ceph RBD, Rook and OpenShift Data Foundation | Native RBD diff/export-diff can describe changes and zeroed extents. Ceph-CSI documents RBD snapshot metadata with the required Ceph version, sidecar and service. Check the packaged driver, whether the service is enabled and whether the mover keeps the parent it needs. CephFS and RBD have different interfaces. [Ceph RBD](https://docs.ceph.com/en/tentacle/man/8/rbd/) · [Ceph-CSI CBT](https://ceph.github.io/ceph-csi/rbd/deploy/#changed-block-tracking-cbt) |
| Standard Linux NFS | An ordinary NFS client has no standard snapshot-to-snapshot changed-block feed. The upstream NFS CSI driver can implement a snapshot by archiving files on NFS. A file mover may reuse chunks after a scan. For a VM disk on that share, a QEMU-aware mover can use VM tracking instead. [NFS CSI snapshot parameters](https://github.com/kubernetes-csi/csi-driver-nfs/blob/master/docs/driver-parameters.md) · [CSI scope](https://kubernetes-csi.github.io/docs/changed-block-tracking.html) |
| NetApp ONTAP and Trident | For NAS, SnapDiff v3 supplies changed **file** information to integration partners. SnapMirror Cloud can transfer changed volume blocks to object storage. Trident Protect separately documents backup from a snapshot using Kopia or Restic. Verify which path your policy selected. [SnapDiff](https://kb.netapp.com/on-prem/ontap/DP/SnapDiff/SnapDiff-KBs/What_is_SnapDiff) · [SnapMirror Cloud](https://docs.netapp.com/us-en/ontap/concepts/snapmirror-cloud-backups-object-store-concept.html) · [Trident Protect](https://docs.netapp.com/us-en/trident-2606/trident-protect/trident-protect-protect-apps.html) |
| IBM FlashSystem and Fusion | A FlashCopy mapping can track changes on the array. IBM Fusion Backup & Restore 2.9 has a separate, documented Ceph RBD block-mode path that queries changed blocks and feeds them to Kopia for backup to object storage. These are distinct products and restore paths. [IBM FlashSystem](https://www.redbooks.ibm.com/redbooks/pdfs/sg248543.pdf) · [IBM Fusion, pp. 68–69](https://www.redbooks.ibm.com/redbooks/pdfs/sg248582.pdf) |
| Dell PowerStore and PowerScale | PowerStore Storage Direct supports incremental transfers to Data Domain. PowerScale OneFS separately exposes changed regions of a named file between snapshots. A Kubernetes mover needs explicit integration with the chosen array and interface. [PowerStore and Data Domain](https://www.dell.com/en-us/infohub/articles/dell-powerprotect-data-manager-data-protection-for-dell-powerstore-storage-arrays) · [OneFS changed ranges](https://www.dell.com/support/manuals/en-us/isilon-onefs/ifs_pub_onefs_api_reference/snapshot-changelists-changelist-resource?guid=guid-d1840fe3-0faf-4582-9695-d9c001f09731&lang=en-us) |

## What popular backup tools consume

| Product | Documented behavior |
| --- | --- |
| Velero 1.19 | The block data mover can read CSI allocated or changed ranges. The release explicitly identifies Ceph RBD as a case where it cannot retain the previous snapshot as needed and falls back to reading **all allocated blocks** for an incremental. Velero also offers filesystem data movement with different read costs. [Velero release notes](https://github.com/velero-io/velero/releases/tag/v1.19.0) · [Data movement](https://velero.io/docs/v1.19/csi-snapshot-data-movement/) |
| Red Hat OADP 1.6 | This distribution uses Velero 1.18. OADP 1.6.2 documents its own Technology Preview for QCOW2 VM incrementals with disk CBT and the appropriate volume policy. Upstream Velero’s release date alone does not change the OADP support level. [OADP release notes](https://docs.okd.io/5.0/backup_and_restore/application_backup_and_restore/release-notes/oadp-1-6-release-notes.html) · [Component versions](https://github.com/openshift/oadp-operator/blob/oadp-dev/PARTNERS.md) |
| Veeam Kasten 9 | The ordinary Ceph CSI block export uses allocation information to skip holes. Kasten documents a different VM CBT export in Technical Preview on OpenShift Virtualization 4.22+, requiring a running VM, matching checkpoint, VM export policy and supported destination. [Ceph integration](https://docs.kasten.io/latest/install/storage/#ceph) · [VM protection and export limits](https://docs.kasten.io/9.0.10/usage/vm_protection/) |
| Trilio for Kubernetes | Its documented CSI path produces a QCOW2 base and incrementals on backup media for restoration into fresh volumes. Its VM guide lists KubeVirt CBT as roadmap work. The file format alone cannot tell you whether the mover reread the source disk. [Backup and restore process](https://docs.trilio.io/kubernetes/5.0.x/t4k-concepts/backup-and-restore-process) · [Virtualization guide](https://trilio.io/openshift-virtualization/cloud-native-virtualization/) |
| Commvault | Its Kubernetes guide describes CSI snapshots and temporary volumes for VM protection and a labeled VM CBT workflow for incremental reads. Match the documented VM workflow to your installed version and storage. [Commvault backup process](https://documentation.commvault.com/v11/software/backup_process_for_kubernetes.html) |

These are upstream and vendor descriptions. For Vesta, use the [current storage matrix](storage-compatibility.md) and [qualification roadmap](../../ROADMAP.md). For a new combination, measure source bytes, uploaded bytes and repository growth separately, then recover into fresh storage without depending on the source snapshot.
